📋 execution plan — brand support ai agent

hiver sde intern take-home assignment
repo: github.com/AnshitaBaduge/brand-support-ai-agent

⚡ credit-aware workflow: this plan is split into small, self-contained chunks. each chunk produces a committable result so no work is lost if a session ends mid-way. pick up from wherever the last chunk left off.

🎯 what we're building (the big picture)

an ai support agent for a single brand (from twitter customer-support data) that can:

  1. classify incoming customer messages into intents (categories you define)
  2. draft a reply grounded in how the brand historically handled similar issues
  3. decide whether to auto-handle or escalate to a human (with a reason)

then prove it works with evaluation, baselines, failure analysis, and a golden test set.

📦 chunk-by-chunk execution plan

chunk 1 project setup & data download

~15 min start here
  • initialize repo structure (folders: src/, data/, golden_set/, notebooks/, configs/, outputs/)
  • create .gitignore (ignore data files, model weights, api keys, pycache)
  • create requirements.txt with initial dependencies
  • download the twitter customer-support dataset from kaggle
  • do a quick sanity check — row count, columns, sample rows
  • commit: add project skeleton and raw data
what you need: kaggle account (or download manually), python 3.10+, pip

chunk 2 data exploration & brand selection

~20 min
  • load the dataset, understand schema (tweet_id, author_id, inbound, text, etc.)
  • count tweets per brand — pick one with enough volume (500+ threads recommended)
  • reconstruct conversation threads (inbound tweet → brand reply chains)
  • document brand choice and reasoning in decision_log.md
  • save filtered brand data as data/brand_conversations.csv
  • commit: filter dataset for chosen brand

chunk 3 data cleaning & thread reconstruction

~20 min
  • clean text: remove urls, @mentions noise, normalize whitespace
  • reconstruct multi-turn threads (link reply chains using response_tweet_id)
  • create structured format: [customer_msg, brand_reply, ...] per thread
  • handle edge cases: missing replies, broken chains, duplicate tweets
  • save cleaned data as data/clean_threads.json
  • commit: clean data and reconstruct threads

chunk 4 intent discovery & definition

~25 min
  • sample ~200 customer messages, read them manually
  • cluster by topic — identify 8-15 natural intent categories
  • write intent definitions with examples in configs/intents.yaml
  • optionally: use an llm to help cluster, but verify manually
  • log intent taxonomy decisions in decision_log.md
  • commit: define intent taxonomy
tip: keep intents actionable — "billing_issue", "order_status", "technical_problem" rather than vague categories. fewer is better than too many.

chunk 5 golden set creation (part 1)

~30 min
  • sample 150-250 customer messages (stratified by intent if possible)
  • for each: label intent, expected reply quality markers, escalation decision
  • save as golden_set/golden_set.csv with columns: id, text, intent, should_escalate, escalation_reason, notes
  • write annotation guidelines in golden_set/annotation_notes.md
  • commit: add golden evaluation set (part 1)
important: these must be genuinely hand-labelled by you. do not auto-generate labels. the assignment explicitly tests this.

chunk 6 intent classifier — baseline

~25 min
  • implement trivial baseline: random or most-frequent-class classifier
  • implement simple baseline: keyword/regex matcher or tfidf + logistic regression
  • evaluate both on golden set — accuracy, f1, confusion matrix
  • log results in RESULTS.md
  • commit: add intent classifier baselines

chunk 7 intent classifier — llm-based

~25 min
  • implement llm-based intent classifier (few-shot prompting with intent definitions)
  • evaluate on golden set — compare against baselines
  • try prompt variations, log what works
  • update RESULTS.md with comparison table
  • commit: add llm intent classifier

chunk 8 reply generation

~30 min
  • implement reply generation using llm with brand's historical replies as context
  • retrieval: find similar past threads using embedding similarity or keyword search
  • prompt: "given this customer message and how the brand handled similar issues, draft a reply"
  • generate replies for golden set examples
  • commit: add reply generation pipeline

chunk 9 escalation logic

~20 min
  • define escalation criteria (e.g., high-emotion, account-specific, legal, multi-issue)
  • implement escalation router — rule-based + llm confidence check
  • evaluate on golden set (precision/recall on escalation decisions)
  • log escalation criteria decisions in decision_log.md
  • commit: add escalation router

chunk 10 evaluation harness — automated metrics

~25 min
  • implement src/evaluate.py — run all components end-to-end on golden set
  • metrics: intent accuracy/f1, reply bleu/rouge, escalation precision/recall
  • output a structured results json and summary table
  • commit: add evaluation harness

chunk 11 evaluation harness — llm-as-judge

~25 min
  • implement llm-as-judge rubric for reply quality (tone, accuracy, helpfulness, safety)
  • run judge on golden set replies
  • manually score ~30 replies yourself, compute judge-vs-human agreement (cohen's kappa)
  • log agreement evidence in RESULTS.md
  • commit: add llm-as-judge evaluation

chunk 12 failure analysis

~20 min
  • review all errors/failures from evaluation
  • identify top 5 failure modes with real examples
  • write hypotheses for each failure
  • write "what is misleading about my headline number?" section
  • update RESULTS.md
  • commit: add failure analysis

chunk 13 decision log & report

~20 min
  • compile decision_log.md — 10-15 non-obvious decisions with reasoning
  • write report sections in README: problem framing, results vs baselines, failure analysis, what's next
  • ensure README lets reviewers reproduce headline results in under 15 minutes
  • commit: finalize report and decision log

chunk 14 final polish & submission

~15 min
  • test full pipeline from scratch (clone → install → run → results)
  • clean up code, remove dead code, check all files are committed
  • update all documentation files (AGENTS.md, RESULTS.md, README.md)
  • submit via the notion form
  • commit: final cleanup for submission
